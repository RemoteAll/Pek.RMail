# Pek.RMail 第四轮审计：队列重启竞态与附件内存（2026-10-25）

> 延续第三轮闭环后用户要求“请继续”的增量审计；本轮只改 Mail，公共库无需变更。
> 代码提交：`a94d346`（已推 main）。

## 1. 发现与修复

### 1.1 队列停止后立即重启可能产生两个工作线程（P1 竞态）

`stop_timeout` 超时会把旧线程分离并把 `running=false`，若调用方立刻 `start`，
旧线程此前读到的停止标志可能已被新 `start` 复位，导致新旧两个线程同时消费队列。
同时旧线程退出时会把新线程的 `running` 清成 `false`。

修复：用 `epoch: AtomicU64` 作为运行代次——
- `start` 先递增代次再置 `running=true`；
- `stop_timeout` 递增代次作为停止信号；
- 工作线程只在代次匹配时继续循环，退出时也只在代次仍匹配时清 `running`。

回归：`queue::tests::stale_worker_does_not_clear_running_after_restart`
直接构造旧代次工作线程，模拟重启后释放发送，断言旧线程退出不清新线程的运行标记。

### 1.2 每次账号尝试深拷贝整封邮件（P2 内存/CPU）

`SmtpEmailSender::send_message` 原来为了覆盖 `from`/`from_name`/`reply_to`
先 `message.clone()`；`send_temporary` 也会先克隆一次。`MailMessage` 含附件时，
一次克隆会整份复制内存附件（默认单附件可达 25MB），多账号 fallback 时反复复制。

修复：
- `build_message` 改为接收 `from`/`from_name`/`reply_to` 覆盖参数，直接读取原邮件；
- `send_temporary` 只计算发件人字符串，不再克隆邮件；
- fallback 复用同一份配置快照调用 `send_with_settings`。

效果：每次账号尝试的附件复制次数从 1 次降为 0 次（MIME 构建时仍读取一次附件内容）。

### 1.3 多附件叠加缺少总量上限（P2 资源安全）

单附件已有 25MB 上限，但多个附件仍可叠加到数百 MB。
新增 `DEFAULT_MAX_TOTAL_ATTACHMENT_BYTES = 50MB`：
- `Attachment::size()` 取文件元数据或内存长度；
- `build_message` 在读取附件前先汇总总量，超限直接返回 `MailError::Attachment`；
- 单附件读取仍由 `DEFAULT_MAX_ATTACHMENT_BYTES` 保护。

回归：`sender::smtp::tests::total_attachment_budget_is_enforced`（用 4+4 字节附件和 7 字节预算验证边界）。

## 4. 仍接受/延后的项

| 项 | 原因 |
|---|---|
| 每个账号尝试仍重新构建 MIME | 不同账号的 From/Reply-To 不同；当前只在真正尝试发送时构建，失败账号通常连接阶段就报错 |
| SMTP 连接池 | 当前发送频率低，与 C# 每次新建连接一致；高吞吐场景再单独立项 |
| `parse_mailbox` 简化解析 | 已覆盖常用 `"昵称 <a@b.com>"`；换用 lettre 解析器会改变接受范围 |
| `reload_if_changed` 约 49µs/次 | 文件元数据固有成本，已在 API 文档写明按秒级调用 |

## 5. 结论

- 本轮修复了一个可复现的线程生命周期竞态与两处附件内存风险。
- 未新增 `unsafe`；生产代码仍仅固定 MIME 一处 `expect`。
- Mail 侧当前无新的 P1/P2；继续保留的均为明确接受/延后项。
